# ADR-0002 多端收听进度的冲突合并

- 状态：已采纳
- 日期：2026-10-23

## 背景

同一个用户会用网页、手机、平板交替听同一本书。网络可能中断，设备时钟可能不准，客户端可能离线数小时后再补传。需要一个**可预测、无需用户干预**的合并规则，避免「听了半小时，换设备却回到一小时前」。

## 决策

**客户端权威 + 最后写入胜（LWW）+ 单调不回退 + 显式跳转豁免**。

服务端 `PUT /progress/{book_id}` 合并伪代码：

```python
def merge(old, new):
    # 1. 时间单调：旧数据直接拒绝
    new_ts = sane_ts(new.client_updated_at)      # 与服务器时间差 >5min 则取服务器时间
    if old and new_ts <= old.client_updated_at:
        return old, accepted=False

    # 2. 显式跳转（用户点章节/拖进度条）无条件采纳
    if new.explicit_seek:
        return new, accepted=True

    # 3. 同一轨且回退超过容差 → 视为旧设备补传，保留较后位置
    if old and old.track_id == new.track_id and new.position_sec < old.position_sec - 30:
        return old, accepted=False

    # 4. 其它情况（前进 / 跨轨 / 首次）采纳
    return new, accepted=True
```

关键点：

- **时间基线用 `client_updated_at`**，但先做「合理性校正」：与服务器时间偏差 > 5 分钟时用服务器接收时间，防止某台设备时钟错乱永久压制其它设备。
- **30 秒容差** 处理「暂停后重新打开进度条抖动」这类微小回退。
- **跨轨回退**（从第 10 章回到第 3 章）视为普通前进，直接采纳——因为跨轨回退通常是真的在重听。
- **响应始终返回服务端权威值**，客户端必须回写本地并以响应为准（这是收敛的保证，不能只做本地乐观更新）。
- **离线补传**：客户端按 `client_updated_at` 升序批量提交，服务端逐条合并，天然幂等（重复提交同一条会被规则 1 拒绝）。
- **「从头重听」** 必须走 `DELETE /progress/{book_id}` 或带 `explicit_seek=true`，否则会被防回退规则挡住。

## 后果

**正面**
- 无冲突弹窗、无「以哪台设备为准」的选择题，用户体验一致。
- 实现简单（不到 40 行），可完全单测覆盖。
- 天然支持离线补传与重复提交。

**负面**
- 用户若在某设备上**默默**往回听超过 30 秒且未触发 `explicit_seek`（例如连续点按后退按钮），位置可能被另一台设备的较后进度覆盖。缓解：所有 UI 上的「跳转」动作都显式置 `explicit_seek=true`，仅有「自动续播」不置位。
- 依赖客户端时钟质量（已用 5 分钟校正兜底）。
- 无法表达「两地同时听不同章节」——但这本就是用户意图模糊区，LWW 是合理默认。

## 备选方案（已否决）

| 方案 | 否决原因 |
|---|---|
| 服务端只保留最大位置 | 无法「重听」，且章节跳转体验差 |
| 每设备独立进度，用户手动选 | 增加 UI 复杂度，用户不想理解 |
| CRDT（如 LWW-Register 库） | 对单值进度是过度设计，且不解决「回退语义」 |
| 服务端时间戳为准 | 离线补传的顺序会全乱，晚到的旧数据会覆盖新进度 |
